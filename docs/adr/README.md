# 判断の記録（ADR）

このプロジェクトで合意した判断と、その理由を記録する台帳である。
作業者（人・エージェント）は、作業の前に関係する ADR を確認し、合意済みの判断を前提として扱う。

## 何を ADR に書くか

設計や開発の進め方を左右する判断で、後から「なぜそうしたか」を確かめる必要があるものを書く。
判断ごとに、書く場所を次のように一つに決める。

| 判断の種類 | 書く場所 |
| --- | --- |
| 方式・技術・構成の選択（採用するライブラリ、データの保存方式など） | ADR |
| 開発の進め方・作業範囲・保証範囲の合意（対象外とする環境、人の確認が要る境界など） | ADR |
| 製品が満たす機能・制約 | [要件と受入条件](../requirements/catalog.md)（FR・NFR） |
| 作業の仕方・文書の書き方の規則（使う言語、コミットの単位など） | [AGENTS.md](../../AGENTS.md)・[執筆・編集ガイドライン](../development/documentation-guidelines.md) |
| まだ決まっていない問い | [開発課題](../development/issue-management.md) |

ADR には判断と理由を書き、確定した仕様の詳細（版の一覧、データ形式など）は設計文書に書いて ADR からリンクする。
同じ判断を ADR と設計文書の両方に書かない。

## 一覧

まだ ADR はない。
追加したら、次の形式で表へ1行ずつ加える。

```markdown
| 判断 | 主題 | 状態 |
| --- | --- | --- |
| [ADR-0001](0001-主題を表す英語名.md) | 判断の内容を一文で書く | 合意済み |
```

## 書き方

ファイル名は `0001-主題を表す英語名.md` のように、4桁の番号と英小文字・ハイフンの名前にする。
番号は再利用しない。
判断を変えるときは、元の ADR を書き換えずに新しい ADR を起こし、元の ADR の状態を「ADR-0002 で置き換え」とする。

必須は「状態」「背景」「判断」の3つで、短い判断はこれだけでよい。
代替案を比べた場合や、影響が大きい場合は「比較した案」「帰結」を加える。

```markdown
# ADR-0001: 判断の内容を一文で書く

- 状態: 合意済み
- 関連: FR-001、[設計文書の名前](../design/設計文書.md)

## 背景

判断が必要になった事情と、守る条件を書く。

## 判断

決めた内容と、その適用範囲を書く。

## 比較した案（任意）

検討した代替案と、採らなかった理由を書く。

## 帰結（任意）

得るもの・失うもの・増える運用負担と、確かめ方を書く。
```

状態は「提案」「合意済み」「ADR-0002 で置き換え」「廃止」のいずれかにする。
「提案」は、合意を待つ判断の案を文章にした状態である。
判断が決まるまでの状況（誰の回答を待つか、何が決まれば完了か）は設計判断の [開発課題](../development/issue-management.md) で管理し、合意したら ADR を「合意済み」にして課題を完了にする。
合意済みでも未完了の範囲がある場合は、状態の後ろに書き添える。
例えば「合意済み。実機での確認は未実施」のように書く。
利用者が方式を直接指定した場合は、状態を「合意済み（利用者の指定）」とする。
