# 執筆・編集ガイドライン

このプロジェクトの要求・設計・運用・参照・検証文書と、ADR・開発課題の作成、編集、構成レビューに適用する。
読者が現在の仕様と必要な判断根拠を理解できる構成にする。
文書の新設・構成変更では目的と読み順を検討し、局所的な修正では変更箇所と影響する参照を確認する。

## 1. 読者の目的と文書の役割

文書を新設・再構成するときは、誰が何を知り、読後に何を判断・実行するかを定める。
必要な前提、説明順、詳細の参照先から構成を決め、既存のファイル分割・名称・配置に縛られない。

| 状況 | 構成の判断 |
| --- | --- |
| 一つの判断に複数文書の往復が必要 | 一連の説明を統合するか、流れを通して読める入口を設ける |
| 読者・目的・責務が混在する | 目的ごとに分ける |
| 同じ規則の詳述や独立した目的のない文書がある | 定義元へ集約し、他は要約と参照にする |
| 内容を末尾へ追加すると説明順が崩れる | 本来属する章へ組み込む |

ファイル数や行数だけで分割しない。
文書の役割と必要な内容を次のように整理し、定義元を一つにする。

| 役割 | 主な内容 |
| --- | --- |
| 要求 | 実現すること、制約、受入条件 |
| 設計 | 責務、処理、状態、判断条件と理由 |
| 運用 | 人が確認・操作する手順、結果、異常時の対応 |
| 参照 | インターフェース・データスキーマ等の詳細定義、製品仕様 |
| 検証 | 保証する性質、ケース、観測方法、合否の根拠 |
| ADR | 判断と適用範囲、理由、代替案、トレードオフ |
| 開発課題・開発計画 | 判断・検証・不具合・改善・作業の条件と結果、次の作業と依存関係 |

この区分はファイル構成を固定するものではない。
索引・リンクは内容が分かる名前にし、ID には短い説明を添える。
要約から定義元へ直接リンクし、規則全文の複製や循環参照を避ける。

### 配置と命名

総合入口はリポジトリルートの README とし、共通の初読経路と目的別の入口を示す。
各領域の入口は読む順序と索引を扱い、仕様・契約の詳細は本文の定義元へ置く。

| 配置 | 収める内容 |
| --- | --- |
| `docs/requirements/` | このプロジェクトの機能・制約・受入条件 |
| `docs/design/` | 設計の原則、全体設計、機構別設計、外部製品との連携・採用条件 |
| `docs/adr/` | 判断の記録（ADR）。方式の選択と、進め方・範囲・保証範囲の合意 |
| `docs/development/` | 開発計画・執筆基準、課題、検証、記録（レビュー・調査・検証の結果） |

利用者向けの手順（`docs/guides/`）や、インターフェース・データ契約（`docs/design/contracts/`）など、必要になった領域は同じ考え方で追加する。

`design`・`development`・`verification` は分野・活動名をそのまま使う。
独立した文書・記録の集合には `requirements`・`guides`・`contracts`・`issues`・`records` 等の複数形を使い、定着した略称の `adr` は維持する。
一般文書の読む順序は目次で管理し、ファイル名に並び順の番号を付けない。
ADR・課題等の識別番号は読み順とは別に扱う。
課題の配置・索引・管理方式は [開発課題の管理](issue-management.md) を定義元とする。

新しい文書は独立した読書目的がある場合に作り、主たる掲載先を一つ定める。
一つの判断に必要な連続した説明は同じ文書へ組み込み、別テーマの入口からはリンクで共有する。
機構別設計から、関係する要求・契約・検証ケース・ADR へ直接進めるようにする。
説明文書の冒頭には目的、必要な前提、最初に読む範囲を示し、詳細を調べる範囲と区別する。
辞書・索引・入力テンプレートには、その用途に合う案内を置く。
台帳（要件・ADR・設計・検証の索引・記録）の見本は、書式の定義として残す。
最初の1件を加えるときに、「まだ〜はない」の文を実際の表や一覧へ置き換える。

## 2. 説明の順序

入口に文書の目的と必要な読み順を置き、初めて読む人への導線と目的別の索引を分ける。
本文は「目的・全体像 → 用語と具体例 → 通常の流れ → 判断条件・例外 → 詳細契約」を基本とし、辞書・索引・入力テンプレート等は用途に合わせる。

- 概念は初出で説明する。異なる分類軸の概念は、共通の具体例で関係を示す。
- 利用者向けの説明は、利用者が見る情報・行う操作・得る結果を先にし、内部の記録は理解に必要な位置で示す。
- 入力は記入順に並べ、必須・任意・既定値・例を区別する。
  人が用意する資料と、システムが生成する資料を混ぜない。
- 報告は出力例から、試験は要求・計画・実行証拠・完成判定のつながりから説明する。
  同種の契約は、目的・入出力・条件・失敗時の扱いを同じ順で記述する。

## 3. 現在の仕様と判断根拠

文書は現在の要求・仕様・方針・制約と、その理解に必要な理由を説明する。
リリース前後を問わず、改訂履歴・設計作業の経緯は本文へ混ぜず、Git の履歴で確認する。
ADR も作業報告の追記先にしない。

「設計を追加した」「レビューを反映した」ではなく、誰が何を処理し、どの条件を守るかを書く。
理由は「期限が切れた承認で変更を反映しないため」のように、守る性質との関係を示す。
実行時の監査・失敗・承認履歴、互換性・移行の規則は仕様として保持する。
外部製品の調査日・対象版・出典や検証条件も、適用範囲を判断するために必要なら記載する。

提案・合意・未決を区別し、検査で確かめた範囲は [検証方針](verification/strategy.md#確かめる保証の区別) の区分で書く。
外部製品の公開仕様、このプロジェクトの採用案、実機で確認した能力を同じ確度で書かない。
構成レビューは要求・契約・合意範囲の意味を維持し、技術的な再審査を自動的に追加しない。
技術判断が必要な問題は編集判断と分けて扱う。
保存を求められたレビューは、指摘・改善案・対応状況を独立した [記録](records/README.md) へ置く。
継続的な編集基準はこのガイドラインとする。

## 4. 用語・文章・図表

### 用語

- 論理概念は定義元の名前を使い、本文・表・図で同じ表記に揃える。略称や大小文字の揺れを混在させない。
- 一般的な説明の語と、外部ツール・製品の語を区別する。同じ語を別の意味で使う場合は、初出で区別を示す。
- データ項目・列挙値・コマンド・ファイル名・機械可読キーは、契約どおりの綴りをコード表記で示す。
  概念名へ改名せず、大小文字だけで意味を推測させない。
- このプロジェクト固有の用語は、[全体像](../overview.md) または設計の定義元で定義し、ここには規則だけを置く。

### 段落と文の長さ

**一段落で一つの論点を扱い、最初の文で要点を示す。**
通常は1〜3文を目安にし、4文以上が続く場合は論点の混在や分割の必要を見直す。
文数は編集時の目安であり、機械的な上限にはしない。

- **論点が変わったら段落を分ける**：定義から具体例、通常処理から例外、条件から別の条件への切替を見分ける。
- **一文には一つの主な判断を置く**：主語・目的語を示し、条件や補足を連結しすぎない。
- **理由と結論はつなげて読む**：短くするためだけに一文ずつ孤立させず、条件・理由・例外と適用先の関係を保つ。
- **段落の境界には空行を置く**：Markdown のソースは原則一文ごとに改行するが、通常の改行だけでは表示上の段落は分かれない。

### 文章・箇条書き・表・図の使い分け

内容の関係に合う形式を選ぶ。
段落全体を一つの箇条書き項目へ移すだけでは、情報の密度は下がらない。

| 伝えたい関係 | 使う形式 | 書き方 |
| --- | --- | --- |
| 結論と理由、定義と補足 | 短い段落 | つながりのある説明をまとめる |
| 並列する役割・条件・選択肢 | 箇条書き | 一項目一要点にし、同じ軸と粒度で揃える |
| 順番に意味がある手順 | 番号付きリスト | 各段階で行うことを示す |
| 複数対象を共通の項目で比較 | 表 | 列の比較軸を揃え、セルを短くする |
| 関係・処理順・競合 | 図 | 一つの問いに絞り、矢印の意味を示す |

箇条書きの前には「次のすべてを求める」「条件に応じて選ぶ」等の導入を置く。
必須条件の集合か、選択肢か、単なる例示かを明確にする。

長い項目は、条件と説明を見直し、必要なら小見出しと短い段落へ分ける。
入れ子は階層そのものを示す必要がある場合に限り、太字は項目名や重要な結論へ絞る。

表のセルに条件・例外・手順を詰め込まず、共通の補足は表の前後へ置く。

### 図解を積極的に使う場面

複数の概念や処理のつながりを読者が頭の中で組み立てる必要がある箇所では、図解を積極的に検討する。
特に全体像や機構設計の入口では、関係を見渡せる図から詳細へ進める構成にする。

| 読者が掴みたいこと | 図の選び方 |
| --- | --- |
| 概念の所属・参照・多対多の関係 | 関係図。線と枠の意味を明示する |
| 処理順・条件による進み先 | フロー図。判断条件を分岐へ書く |
| 複数主体の呼出し・応答・待機 | シーケンス図。主体と時間順を分ける |
| 状態と、状態を変える条件 | 状態遷移図。遷移の契機を矢印へ書く |
| 責務・所有範囲・外部との境界 | 構成図。境界の内外と接続を示す |

図を作る前に、その図で答える問いを一つに絞る。
正常な流れ、例外時の分岐、記録の参照関係は必要に応じて別図にし、一枚へ詰め込まない。

- **本文と分担する**：図は関係や流れ、表は項目の比較、文章は理由と注意点を担当する。
  同じ説明を三形式で繰り返さない。
- **図の読み方を添える**：何の図かを直前に示し、矢印・枠の意味と読み取る要点を短く説明する。
  重要な条件は図だけに閉じ込めない。
- **名前と根拠を揃える**：本文・定義元と同じ概念名を使い、概要図から詳細設計へリンクする。
  例示と一般規則を区別する。
- **表示サイズで確認する**：短いラベルと必要な要素へ絞り、文字を縮小して一画面へ押し込まない。
  過大な縦長・横長の図は、問いや範囲を分け直す。
- **Markdown で保守する**：関係図やフロー図は原則 Mermaid で本文と一緒に管理し、別の画像原稿との二重管理を避ける。

図の数を目標にせず、文書の作成・レビュー時に「図があれば関係を理解しやすくなる箇所」を探す。
単純な列挙や短い手順だけで十分な箇所は、箇条書きを使う。

### 小見出し・例・参照

小見出しは、読者が知りたい問いや作業のまとまりに付け、見出し階層を飛ばさない。
一文ごとに見出しを増やすことは避ける。

例は可能な範囲で共通の題材を使い、例示値を本番の閾値・既定値と混同させない。
テンプレートの置換箇所、パスの基準、接続例で検証できる範囲と限界を明記する。
図・表・例に、本文にない仕様や未合意の判断を持ち込まない。

概要には判断に必要な要点を残し、契約の詳細は定義元へリンクする。
短文化のために必須条件や例外を消さず、同じ説明を複数箇所へ複製しない。

## 5. 完了時の確認

変更範囲について次を点検し、検査は変更の影響に応じて選ぶ。
表示の確認（GitHub 等のプレビュー）は、図・表の新設や構造変更、文書構成の変更、表示崩れが疑われる場合に、影響する箇所を対象として行う。
通常の文言・リンク・課題状態の変更は、内容・差分と `npm run check` を基本とし、表示の確認を毎回の完了条件にしない。

- **内容と合意範囲**: 読者が必要な仕様と判断根拠を理解でき、提案・合意・未決と保証範囲を区別し、要求・契約・識別子の意味を保持している。
- **関連文書・参照**: 定義元と参照先が明確で、変更の影響がある文書・リンク・見出し・索引を整合させている。
- **読みやすさ**: 長い段落・箇条書き項目・表のセルへ複数の論点を詰め込んでいない。
  表示を確認する場合は、狭い画面での折返し・はみ出しと、見出しや冒頭文からの辿りやすさも確認する。
- **図解**: 関係・分岐・境界を図で示す必要を検討し、追加・変更した図の表示確認では文字の欠け・大きさを確認する。
  図から読み取れる条件が本文・定義元と一致し、色だけに意味を持たせていない。
- **差分と必要な検査**: 意図した差分を読み直し、変更に応じた検査を行い、実施内容と未確認事項を報告する。
