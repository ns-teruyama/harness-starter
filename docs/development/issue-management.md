# 開発課題の管理

このプロジェクトでやるべきことと、その進み具合を管理する台帳である。
決めること（設計判断）、確かめること（調査・検証）、直すこと（不具合・改善）に加え、設計文書やコードを作る作業も、同じ台帳に課題として登録する。
[開発計画](plan.md) の実装計画（R2）で定める依存順のタスクも、ここに登録する。

課題の正本は Git で管理する個別の Markdown とし、一覧はそこから生成する。
GitHub Issues 等の外部の課題管理は、受付・議論・証拠への参照として使い、正本の代わりにしない。

[README](../../README.md)・[課題の一覧](issues/index.md)

## 配置と採番

ID は種類・状態・リリースによらず `DEV-0001` からの連番とする。
文書間の課題参照は、DEV 番号と個別ファイルへの直接リンクに統一する。
番号は再利用せず、課題ファイルは削除しない。
重複・対応しない課題も、理由を記録して完了にする。

`issues/0001-0100/DEV-0001.md`、`issues/0101-0200/DEV-0101.md` のように100件単位で分割する。
題名変更・完了・再開による改名や移動はしない。
`issues/` の直下には、この分割のディレクトリと生成一覧だけを置く。それ以外の項目は検査で拒否する。
4桁を超えても番号を継続する。

生成一覧は次の2種類で、課題の状態が変わっても課題ファイルは動かさず、一覧の掲載先だけが変わる。

| 生成一覧 | 内容 |
| --- | --- |
| `issues/index.md` | 課題の入口。未完了の課題を、状態と未完了の先行課題つきで1ページに並べ、完了年ごとの一覧へリンクする |
| `issues/closed-2026.md` など | その年に完了した課題を、完了日の新しい順に1ページに並べる |

件数による分割はしない。
作成年で課題ファイルを分けず、特定の年に集中しても同じフォルダーへ数百件を置かない。
索引は閲覧用であり、永続的な参照は個別課題ファイルへ張る。

ID の接頭辞、生成一覧の題名、種類・状態・完了理由の表示名は、`scripts/issues.mjs` 冒頭の `config` で変更できる。
種類・状態の値（`decision` 等）と本文の必須節は検査の前提なので、`config` では変えない。
変更した場合は、この文書と README の記述も合わせて更新する。

## 種類と状態

| 種類 | 値 | 完了条件 |
| --- | --- | --- |
| 設計判断 | `decision` | 必要な関連判断まで決まり、ADR・要件などの定義元へ反映済み |
| 調査・検証 | `verification` | 指定した確認を実施し、結果と証拠を確認済み |
| 不具合 | `bug` | 修正と回帰検証が完了 |
| 改善 | `enhancement` | 事前に定めた受入条件を充足 |
| 作業 | `task` | 成果物（設計文書・コードなど）が完了条件を満たし、必要な検査を確認済み |

作業は、要件・設計・開発計画から導いた、成果物を作る仕事に使う。
既にある成果物をより良くする提案は、改善として登録する。

状態は `open`（未着手）、`in_progress`（対応中）、`deferred`（保留）、`closed`（完了）とする。
完了理由は `resolved`（解決）、`duplicate`（重複）、`not_planned`（対応しない）から選ぶ。
重複・対応しない場合は、修正成功や検証合格を意味しない。

## 課題の記録

ファイル先頭の front matter を、種類・状態・日付の正とする。
front matter には、生成一覧と検査が使う次のフィールドだけを置き、すべて必須とする。
書式は YAML のうち、1行の `キー: JSON値` だけを使う。
文字列は二重引用符、未指定値は `null` とし、複数行の値・暗黙の型変換・未知のキーを受け付けない。

| フィールド | 内容 |
| --- | --- |
| `id`、`title`、`kind`、`status` | 識別・題名・種類・状態。本文の題名と一致させる |
| `recorded_on` | 課題の登録日 |
| `closed_on`、`resolution` | 完了日と完了理由。完了時に必須。未完了時は null |
| `duplicate_of` | 重複で完了した場合だけ、重複先の課題 ID を指定する。それ以外は null |
| `depends_on` | 先に完了している必要がある課題（先行課題）の ID の配列。なければ `[]` |

先行課題は、種類を問わずどの課題にも指定できる。
未完了一覧は、各課題の先行課題のうち未完了のものを示すので、この欄が空の課題から着手できる。
存在しない課題の指定と、先行関係の循環は検査で拒否する。

日付は `YYYY-MM-DD` とする。
本文は「課題」「完了条件」「判断・対応内容」「確認結果」の節を持つ。
front matter に置かない情報は、次のように本文へ書く。

| 情報 | 書く場所 |
| --- | --- |
| 保留の理由・影響範囲・解消条件 | 「保留」の節。保留中の課題だけが持ち、再開・完了のときに節を削除する |
| 作業が対応する要件（FR・NFR）・設計、作る成果物 | 「課題」の節。要件・設計の定義元へリンクする |
| 作業で作った成果物 | 「判断・対応内容」の節。設計文書へのリンクや、コードの変更を特定できる参照（コミット・PR）を書く |
| 不具合の再現手順・期待結果・実際の結果、影響する版 | 「課題」の節。影響する版が未特定なら、調査状況を記す |
| 不具合の修正を含む公開済みの版 | 「確認結果」の節。公開後に追記し、予定版は書かない |
| 外部の Issue・PR 等の参照 | 関係する節へリンクで書く。GitHub の番号を DEV の ID に流用しない |

現在の仕様は要求・設計・ADR の定義元へ反映し、課題には結論と根拠への参照を残す。
完了理由が解決の課題は、完了時に確認結果を記録する。
重複・対応しないで完了する課題は、確認結果の代わりに、その理由を「判断・対応内容」へ記録する。
修正完了とリリース済みは分けて扱う。

対応が不十分だった場合は元の課題を再開し、完了日・理由・重複先を null へ戻す。
過去の完了根拠は本文と Git の履歴に保持し、再開の理由を記す。
別の原因による問題は、関連付けた別の課題として扱う。

## 未決事項の管理ルール

課題対応をどこまで続けるか、合意をどう求めるか、回答の後にどう進めるか、不足する条件をどう扱うかは、[AGENTS.md](../../AGENTS.md#判断の根拠) の「判断の根拠」に従う。
この節は、未決事項を課題としてどう記録するかを定める。

### 合意待ちと保留

必要な合意待ちは同じ課題の対応中（`in_progress`）として扱い、中断・保留・完了に読み替えない。
派生した論点を新しい課題へ分けたり既存の課題へ移したりするだけでは、元の事項を解消済みにしない。
「詳細は後で決める」「実装時に検討する」とした必要な判断も、保留として扱う。

保留する場合は、対象・理由・影響範囲・解消条件を、会話と課題の「保留」の節に明示する。
課題の一部だけを保留する場合も状態を `deferred` とし、本文で決定済みの範囲と区別する。
新たに判明した問題は、同じ作業で解消するか、明示的な保留として記録する。

### 方式の選定と未実施の検証

決定済みの方式と未実施の検証は、区別して記録する。
事前の調査課題には、確かめる不確実性、判断に必要な最小の試作、実製品・権限・認証等の依存条件を記す。
実装後に行う試験は、条件・期待結果を検証ケースとして記録する。
方式を選定した課題は、その試験が未実施であることだけを理由に未決へ戻さない。

### 課題の取り下げと完了

課題が確かめようとする内容が既存の受入ケースと重複し、課題として別に追う不確実性がない場合は、完了理由を `not_planned` として取り下げられる。
受入条件と未実施の状態は受入ケースの側に残るため、取り下げは調査の解決や受入の合格を意味しない。
未確認の方式・保証が残る課題は、参照先へ移すだけでは取り下げない。
取り下げる場合は、理由と参照先を課題の「判断・対応内容」に残す。

完了時は、新たな未決事項が残っていないこと、または明示した保留だけが残っていることを確認する。

## 更新と検査

リポジトリのルートで次を実行する。
補助スクリプト（`scripts/issues.mjs`）は Node.js の標準機能だけを使う開発文書用のもので、本体の実装ではない。

```text
npm run issues:new -- bug "Windowsで再開に失敗する"
npm run issues:build
npm run check
```

`issues:new` は最大 ID の次を採番してひな形を作り、作成したファイルのパスを表示する。
同時作成で ID が競合した場合は上書きせずに失敗するため、更新後に再実行する。
別ブランチでの同一 ID の衝突は統合前に解消し、既に共有した ID を再利用しない。

課題を編集したら `issues:build` で索引を再生成し、`check`（`issues:check` を含む）でメタデータ・配置・索引の一致を確認する。
生成一覧は手で編集せず、生成物と個別の課題を同じコミットへ含める。
`issues:check` は、保留の節・完了理由の記録・確認結果が記入済みであることまでを確かめる。
記入内容の正しさや試験の実施そのものは保証しないため、レビューで本文と証拠を確認する。
外部サービスの状態変更だけで正本の課題を完了にせず、外部への投稿・同期は別途依頼された範囲で行う。
