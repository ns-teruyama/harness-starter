# 開発計画

このプロジェクトをどの順で進め、各段階をいつ終えるかの定義元である。
段階には R0 からの通し番号を付ける。

**現在は要件整理（R0）の段階である。**
要求と機構設計が整い、利用者から実装に進む指示がある段階で本体の実装に着手する。
未決の技術選定や設計案を、確定した前提として実装しない。

文書整理・調査・レビューは、どの段階でも継続してよい。
方式の成立条件を確かめる小さな試作も、本体の実装の着手とは区別して行える。

## 段階別の進め方

| 段階 | 成果物 | 次へ進める条件 | コミット単位 |
| --- | --- | --- | --- |
| R0 要件整理 | [全体像](../overview.md)、[要件と受入条件](../requirements/catalog.md)、[ADR](../adr/README.md) | 要件の漏れ・矛盾を確認し、重要な未決事項を解消し、範囲に合意している | 草案の保存と確定を区別する |
| R1 機構設計 | [設計](../design/README.md)、[ADR](../adr/README.md)、状態遷移、インターフェース・データ契約 | 主要な利用の流れについて、正常時と異常時（失敗・中断・やり直し）の経路を設計で説明でき、[設計全体レビュー](#設計全体レビューの手順と終了条件)の終了条件を満たす | 設計テーマごと |
| R2 実装計画 | 依存順のタスク（[開発課題](issue-management.md)に作業として登録し、先行課題で順序を示す）、[検証方針](verification/strategy.md)に沿った検証ケース、採用構成の固定方針 | 要求 → 設計 → タスク → 検証が対応し、未決事項が実装を妨げない | 計画の基準版 |
| R3 中核の実装 | ドメイン・ユースケース、外部依存の代替（fake）、一連の流れを通す自動試験 | 外部依存を代替した状態で、主要な利用の流れの正常時・異常時のケースに合格する | 機能のまとまりごと |

R4 以降（外部製品との連携、変更・運用の経路、配布など）は、プロジェクトに合わせて段階と条件を追加する。

## 設計全体レビューの手順と終了条件

初回も是正後も、レビュアーは次の順で設計全体を確認する。

1. [要件と受入条件](../requirements/catalog.md)・[ADR](../adr/README.md)から、合意済みの保証範囲を定め、利用者の操作と期待結果を導く。既知の指摘や修正差分との照合は最後に行う。
2. 利用者の入口から結果まで[設計](../design/README.md)を機構ごとにたどり、誰がどの記録を根拠に判断するかを確かめる。例えば同じ注文を二重に受け付けない要件なら、通常の送信に加え、送信直後に通信が切れて再送されたときも同じ注文と識別できるかを確かめる。
3. 設計変更が必要な指摘には、該当要件、具体的な操作順、期待結果、設計から導かれる結果とその根拠を示す。同じ前提から実装者が異なる結果を導ける箇所も指摘に含める。共通する原因があれば、判定の定義元と、その判定を使う他の経路を確認する。保証範囲を広げる提案は新しい要求として扱う。
4. 最後に既知の指摘と照合し、是正の漏れ・再発を確認する。結果には、照合した要件と経路、新規・未解決の指摘、確認できなかった範囲と理由を示す。

指摘件数に上限を設けない。
指摘が出た後も、残る要件・操作経路と、同じ判断を使う他の機構まで照合し、確認した指摘をすべて報告する。
課題を是正する順番は、レビューの対象範囲を縮める理由にしない。

**終了条件**は、合意済みの設計範囲を確認し、そのレビューで新規の実質的な設計指摘が0件、既知の未解決指摘も0件であることとする。
是正後は手順1から再レビューする。
未確認の設計範囲が残る場合は、確認できた範囲に限って結論を示す。
実機での確認を後続段階に置く場合は、設計レビューで期待結果と合否の確かめ方を確認し、試験自体は未実施として記す。

レビューの結果を保存する場合は [記録](records/README.md) に置き、見つかった問題は [開発課題](issue-management.md) として登録する。
