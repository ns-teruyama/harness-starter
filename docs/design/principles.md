# 設計の原則

方式を選ぶとき、機構を追加・変更するとき、不具合を直すときに確かめることの定義元である。
設計文書を書く前と、設計・修正の案を利用者へ示す前に読む。

層の責務と依存方向は [責務と依存方向](architecture.md)、設計全体のレビュー手順は開発計画の [設計全体レビューの手順と終了条件](../development/plan.md#設計全体レビューの手順と終了条件) を参照する。

## 保証範囲を先に決める

方式を選ぶ前に、達成したい結果、守る条件、許容できる損失・やり直し・人の介入を確認する。
通常時と障害時の保証範囲を分け、明示されていない保証（損失なし・停止なし・自動での復旧など）を暗黙の要件にしない。
保証範囲の変更は明示的に合意する。
採用方式を成立させるために必要な契約・例外処理は、方式の選定と同じ作業で扱う。

## 追加より先に、既存の活用と整理を検討する

必要な機能・保証を保ち、既存の成果物・標準機能・運用手順の活用と、責務・境界の見直しによる重複の整理を先に検討する。
追加は具体的な不足を根拠とし、将来の可能性だけで汎用の機構を増やさない。
必要な機能を、初期版という理由だけで後回しにしない。

## 全体の複雑度で比べる

変更量やコード行数だけでなく、変更後に独立して管理する状態・規則・制御経路と、故障要因・依存関係・運用負担で全体の複雑度を評価する。
要求を満たす中で、全体がより単純になる案を優先する。
提案は、必要十分な結果と採用理由、保証・利用者の負担への影響を、判断の規模に応じて簡潔に説明する。

## 共通化は意味で判断する

意味と変更理由が共通する契約・判定を集約し、共通化で増える例外・設定・結合も評価する。
見た目の類似だけでまとめない。
特定の利用者・製品・課題だけに効く場当たり的な例外分岐を、中核へ追加しない。

## 既存の機構を変更する

既存の機構の変更では、責務・不変条件・移行のリスク・回帰の検証を確認する。
不具合は再現条件を特定し、構造上の問題を局所的な迂回処理で隠さない。
修正をどの層へ帰属させるかは、[場当たり的な修正を防ぐ手順](architecture.md#場当たり的な修正を防ぐ手順) に従う。

## 方式の選定と試作を分ける

方式の選定と、実装・検証の実施は分ける。
検証用の小さな実装で調べられることを、本体が未実装であることだけを理由に検証不能としない。
設計検証の補助として書いたコードから、本体の採用技術を決めない。
未実施の検証を課題へどう記録するかは、開発課題の管理の [方式の選定と未実施の検証](../development/issue-management.md#方式の選定と未実施の検証) に従う。
